# Sdysyhj 版本迭代规范（Versioning & Release）

> 适用对象：参与 Sdysyhj 研发流水线的一切智能体（总调度 / 产品 / 研发 / 测试 / 核验）
> 上位规范：[`DevelopmentGuidelines/development-guidelines.md`](../DevelopmentGuidelines/development-guidelines.md)——本文件是其发版环节（第一部分 §8 Git 与证据链、第二部分 §4 交付时序）的操作细则；两者冲突时以上位规范为准。
> 状态：生效中 ｜ 修订需人类批准（同上位规范尾注约定）
> 基线：本文件生效时最新已发版本 **0.1.0**（MVP），下一版为 **0.1.1**。

---

## 1. 目的与范围

把"版本号怎么定、何时递增、发版要做哪些动作、谁来做"固化为可执行纪律，避免各 Agent 凭记忆操作导致版本号、CHANGELOG、tag、安装包四处不一致。覆盖：

- 版本号规则与 **0.1.x 锁定**（当前人类决策）
- 版本号的所有载体与一致性检查
- 发版的定义、触发条件与固定剧本
- CHANGELOG 条目格式
- 角色分工与禁止事项

不在本文件范围：代码交付与核验流程本身（见上位规范第二部分 §4/§5/§8）、GitHub 平台层操作细则（见 `github-operations.md`）。

## 2. 版本号规则（0.1.x 锁定）

### 2.1 格式与当前锁

- 版本号格式：`MAJOR.MINOR.PATCH`（语义化版本三段式）。
- **当前锁定 `0.1.x`**：`MAJOR=0`、`MINOR=1` 两段冻结，仅第三段 `x`（PATCH）可变。这是人类的版本决策，任何 Agent 不得变更。
- 唯一事实来源（single source of truth）：`package.json` 的 `version` 字段。其余载体（§3）一律从此派生，禁止各自维护。

### 2.2 递增规则

1. **每次发版 `x` 严格 +1**：`0.1.0 → 0.1.1 → 0.1.2 → …`，连续递增。
2. **禁止跳号**：不允许 0.1.2 直接跳到 0.1.4（哪怕"留号备用"）。
3. **禁止复用与回退**：一个版本号只对应一次发版；已发版本的 tag、CHANGELOG 条目、安装包一经产出即冻结，不得重打、改写或回退版本号。
4. **开发期间不递增**：开发/修复/核验回路进行时，`package.json` 保持**最后已发版本号**；递增动作只发生在发版提交（见 §5 步骤 2）。失败回路（FAIL → 修复 → `ready-for-verify-rN`）期间版本号一律不变。

### 2.3 解锁条件（升 0.2.0 / 1.0.0）

- 升级次版本（0.2.0）或主版本（1.0.0）属于**重大版本决策**，只能由人类发起或批准。
- 批准后由总调度修订本文件 §2.1 的锁定基线并留修订记录，之后按新锁定段位继续"每次发版 +1"。
- 在此之前，任何角色提出的 0.2.x / 1.x 提案一律退回，不进入流水线。

## 3. 版本载体与一致性（五处一致）

| # | 载体 | 形态 | 说明 |
|---|---|---|---|
| 1 | `package.json` | `"version": "0.1.x"` | 唯一事实来源 |
| 2 | `CHANGELOG.md` | `## 0.1.x — <主题>` 条目 | 每版一条，置于文件顶部（§6） |
| 3 | git tag | `v0.1.x`（annotated） | 发版锚点，由总调度打（§5） |
| 4 | 安装包 | `sdysyhj-0.1.x.vsix` | 文件名即版本；不入库（`.gitignore` 含 `*.vsix`） |
| 5 | GitHub Release（如启用） | 标题 `v0.1.x` | 操作走 `github-operations.md` 通道 |

一致性纪律：

- **发版验收时五处（或启用四处）必须一致**；任何一处不一致即发版不合格，退回修正。
- 发版标签 `v0.1.x` 与核验锚点 `ready-for-verify[-rN]` 是**两套标签、两个用途**：后者是流水线内核验检出的临时锚点（上位规范 §8.2），**不构成发版**；一个版本号只对应一个 `v` 标签，`ready-for-verify` 轮次多少与版本号无关。
- 一致性检查命令（总调度发版时执行并留痕）：

```bash
grep '"version"' package.json          # ①
head -n 5 CHANGELOG.md                 # ②
git tag -l 'v*'                        # ③
ls sdysyhj-*.vsix                      # ④
```

## 4. 发版的定义与触发

- **发版 = 一个版本号 + 对应 tag + CHANGELOG 条目 + vsix 产物的正式产出**。代码合入（commit）本身不等于发版。
- **默认触发**：某批次任务走完流水线——核验报告逐 FR PASS + 总调度交付验收通过（上位规范第二部分 §4 ⑥、第一部分 §7.4）——即触发一次发版，`x` +1。
- **批次归并**：多个小闭环（如数个缺陷修复）可合并为一版发出，由总调度在任务单裁决并留痕；但禁止同一闭环拆成多版、禁止一版对应无留痕的多个来源。
- **已发版后发现缺陷**：不改历史——不开"补发""改包"口子，走新版本 `0.1.(x+1)`（缺陷单 → 修复 → 核验 → 发版，流程照旧，可裁剪用例范围但须在任务单裁决留痕）。

## 5. 发版剧本（固定步骤，顺序执行）

| 步骤 | 动作 | 执行者 |
|---|---|---|
| 1 | 前置确认：核验报告逐 FR PASS、交付验收完成、任务单闭环信息齐全 | 总调度 |
| 2 | `package.json` `version` 递增为 `0.1.(x+1)` | 研发 Agent |
| 3 | `CHANGELOG.md` 顶部新增该版本条目（格式见 §6） | 研发 Agent |
| 4 | 全量自测：`npm run typecheck` / `npm run build` / `npm run verify:unit` / `npm run verify:integration` 全绿，输出摘要留任务单 | 研发 Agent |
| 5 | 打包：`npx @vscode/vsce package`，核对产物名为 `sdysyhj-0.1.(x+1).vsix`；旧版 vsix 移出工作区根目录或删除（根目录同一时间只保留最新一版，防误装） | 研发 Agent |
| 6 | 一致性检查（§3 四条命令）+ 推送前密钥扫描（上位规范 §8.3） | 总调度 |
| 7 | 提交：commit 信息 `chore(release): v0.1.(x+1)`，正文注明任务单链接与核验报告链接；打 **annotated** tag `v0.1.(x+1)`（注明发版结论）；push（commit 与 tag） | 总调度 |
| 8 | （如启用）GitHub Release：以 `v` 标签建 Release，正文贴 CHANGELOG 条目 + 报告链接，操作走 `github-operations.md`；任务单补发版留痕 | 总调度 |

> 说明：`vsce` 未列入 devDependencies，按需以 `npx @vscode/vsce` 执行；若环境不可用，报告总调度换通道，禁止静默改用其他打包方式。

## 6. CHANGELOG 条目规范

沿用现有格式（见 `0.1.0` 条目）：

```markdown
## 0.1.x — <一句话主题>

- <变化点 1>
- <变化点 2>
- …
```

1. 新版本条目**插入文件顶部**（最新在上）；`# Changelog` 标题保留在最上方。
2. 一行主题概括本版性质（如"MVP / Diff & Apply / 缺陷修复批次"）。
3. 要点列表**以用户可见变化为主**（新增 / 修复 / 改进 / 行为变化）；纯内部重构可简列或合并为一条，不逐文件罗列。
4. **可溯源**：缺陷修复注明缺陷单号（如 #D-NN）或 Issue 链接；功能注明对应 FR 编号或任务单；禁止"修复若干问题"式空泛表述。
5. 条目一经发版即冻结；勘误在后续版本条目中说明，不改写已发条目。

## 7. 角色分工

| 角色 | 发版相关职责 |
|---|---|
| 总调度 | 发版触发与批次归并裁决；§5 步骤 1/6/7/8（git 写操作唯一执行人）；一致性核验 |
| 研发 Agent | §5 步骤 2-5（`package.json` 属其可写工程文件；CHANGELOG 为发版配套产物，仅发版提交中改动） |
| 产品 Agent | 不触碰版本载体；需求规划中涉及版本目标时引用本文件锁定口径 |
| 测试 Agent / 核验 | 不触碰版本载体；核验发现版本不一致（如 vsix 名与 tag 不符）按缺陷上报 |

## 8. 禁止事项

1. 禁止任何角色擅自解锁 `0.1`（发 0.2.0 及以上）——属人类决策（§2.3）。
2. 禁止跳号、复用、回退版本号；禁止"先占号后开发"。
3. 禁止版本载体不一致的交付（五处一致是发版门禁，§3）。
4. 禁止把 `ready-for-verify[-rN]` 当作发版或版本依据。
5. 禁止无 CHANGELOG 条目、无 `v` 标签的"口头发版"；发版动作必须在任务单留痕。
