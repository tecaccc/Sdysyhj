## 第一部分 · 操作规范

## 0. 六条底线（任何时候不可违反）

1. **写权限即边界**：只写自己角色名下的文件；越界写入 = 交付不合格，退回重做（以 git 历史认定）。
2. **产物契约即接口**：角色之间不通过对话交接结论，只通过仓库内固定格式的文件交接；口头/汇报文本不构成依据。
3. **证据即事实**：任何 PASS/FAIL/完成声明必须附可复现证据（命令输出、脚本原文、文件路径）；"应该通过"式表述无效。
4. **确定性即质量**：任何人、任何时刻重跑，结果必须一致；间歇性失败（flaky）按缺陷处理，禁止带病交付。
5. **独立即可信**：自测 ≠ 核验；核验不得采信开发自述（包括开发自写的测试，只能作佐证）。
6. **变更即留痕**：基线修订、裁决、故障、通道切换，一律写入 `docs/tasks/` 任务单并在 git 留痕；禁止静默修改。

## 1. 角色与写权限矩阵（硬约束）

| 角色 | 可写 | 禁写（重点） | git 操作 |
|---|---|---|---|
| 总调度 | `docs/tasks/`、流程文档（经人类批准） | 一切角色产物 | **唯一提交人**（代所有角色 commit/tag） |
| 产品 Agent | `docs/requirements.md` | `src/`、测试、核验报告 | 无 |
| 研发 Agent | `src/`、`webview/`、`media/`、`test/`、工程文件（package.json、tsconfig、esbuild、.gitignore、README…）、`docs/technical-design.md` | `docs/requirements.md`、`docs/test-cases.md`、`docs/verification/`、`docs/tasks/`、`DevelopmentGuidelines/`（规范文档） | 无 |
| 测试 Agent（用例） | `docs/test-cases.md` | 一切实现侧内容（含 `test/`、`package.json`、`docs/technical-design.md`） | 无 |
| 测试 Agent（核验） | `docs/verification/`、`docs/verification-plan.md` | 源码、用例、需求 | 无 |

补充规则：

- **git 写操作统一由总调度执行**。子 Agent 一律禁 commit/tag/branch/stash——并行 Agent 共用仓库时 git index 竞争会造成证据链损坏。子 Agent 自检声明中必须写明"无 git 写操作"。
- 子 Agent 的只读 git 命令（`git status`/`git diff`/`git log`）不受限，且**鼓励**用于自检越界。
- 收产物时总调度必须执行 `git status --short`/`git diff --name-only` 权限核验，并把结果写入任务单（实操：曾以此发现日期误写并退回修正）。

## 2. 上下文与独立性纪律

1. **全新上下文**：除"缺陷派回原研发 Agent 修复"外，每个任务的执行者以 fresh context 启动，互不可见对方推理过程。
2. **盲写纪律**（测试·用例阶段）：
   - 仅依据 `docs/requirements.md` + 产物契约（第二部分 §6）；
   - 禁止读取 `src/`、`webview/`、`test/`、`package.json`、`docs/technical-design.md`、`docs/verification/`（含核验报告——其中含实现细节）；
   - 发现需求歧义只上报，不自行脑补实现。
3. **核验独立性**（测试·核验阶段）：
   - 在干净检出（clone/worktree 到 /tmp，检出 `ready-for-verify` 标签，`git status --porcelain` 为空）中执行；
   - 开发自述、开发自写测试只能作佐证，全部重点结论必须独立脚本/命令重测（实战教训：R1 曾出现"归档证据与报告叙述不一致"，R2 以独立 spawn 路径断言消除混淆）；
   - 历史报告仅作缺陷范围参考，每条 TC 重新执行。
4. **通道纪律**：执行通道（工具/代理类型）异常需切换时，先向人类明示再切换，禁止静默换通道；切换后保持同等隔离级别。

## 3. 需求基线与裁决

1. 需求基线（`docs/requirements.md`）一经审批点通过即**冻结**；变更走"基线修订"：影响面评估 → 总调度裁决 →（涉及 FR 范围/优先级变化时向人类通报）→ 产品 Agent 执行修订 → 通知研发/测试双方。
2. **裁决必须落档**：口径裁决写入需求基线 §"验收标准澄清"（编号续号）+ 修订记录行 + `docs/tasks/` 裁决记录；三处一致。
3. **口径优先于实现猜测**：验收标准歧义一律由裁决钉死可判定口径（实战例：消息数 = user+assistant 总数；中止后运行状态回 idle，"已中止"为消息级标记；"提示刷新"须拦截或自动刷新）。
4. 修订记录格式：`日期 | 版本 | 改动点`；版本号语义变更递增 x.y，纯澄清递增 x.y.z 亦可，但**必须**在同一文档内自洽。

## 4. 研发实现规范

### 4.1 工程与架构

- TypeScript strict；esbuild 打包（宿主 bundle + webview bundle 分开）；产物单文件。
- Pi 集成走 **RPC 子进程**（`pi --mode rpc`）：严格 JSONL、只按 LF 切分、禁用 Node `readline`（U+2028/U+29 会错切）；运行时来源解析 = PATH pi（版本探测下限）→ 内置 `dist/cli.js` 回退。
- 进程隔离：agent 崩溃不得波及宿主；子进程崩溃自动重启**一次**，失败给可行动错误。
- 配置归属：provider/model/凭证一律走 pi 自身配置（`~/.pi/agent/`）；插件 settings 仅 UI 项。
- 打包布局必须自检：`<ext>/dist` + `<ext>/node_modules` 真实布局下运行时解析可用（实战教训：require.resolve 受 exports 限制 + 相对路径多一级，vsix 形态必现失败——修复后须以生产布局复现脚本回归）。

### 4.2 安全

- 日志脱敏：`api_key / Authorization / sk-…` 等模式过滤，出通道前 `[REDACTED]`；
- Webview：CSP `default-src 'none'` + nonce + DOMPurify 消毒；
- 不落盘会话副本、不引入遥测；会话/状态仅存 `$HOME/.pi/agent/`。

### 4.3 测试与确定性

- 固定脚本名 **`verify:unit` / `verify:integration`**（契约约定，禁止改名）；全部离线可跑（mock provider / 假子进程），禁真实 API key、禁外网。
- **禁止 flaky**：间歇性失败 = 缺陷。含时序的断言要么给产品侧顺序保证（如事件屏障），要么有界确定性等待；交付前须**并行负载下连跑 10 次全绿**（实战教训：stderr 与 `agent_settled` 竞态在负载下 2/6 失败，被交付验收拦下）。
- 每个缺陷必须有对应回归测试；修复不得放宽既有断言语义。
- 临时断言脚本写在仓库外（/tmp），脚本全文+输出即证据。

### 4.4 交付物

交付（打 `ready-for-verify` 前）必须齐备四件：
1. 自测全绿输出摘要（tsc/build/verify:unit/verify:integration）；
2. **FR 追溯表**（写入 `docs/technical-design.md`）：每条 FR → 实现文件:位置，或"未实现+原因"，P2 标"二期"；
3. 设计偏差清单（若实现偏离技术方案/需求口径，含理由）；
4. 交付汇报（逐缺陷修复说明含根因+改动位置、回归测试清单、自检声明）。

## 5. 测试用例编写规范（盲写）

每条 TC 必含：**TC-id ↔ FR-id 映射、前置条件、确定性操作步骤（Agent 可无人执行的命令/脚本，禁止"人工点击"）、期望结果、判定方式（PASS/FAIL 判据）**。并遵守：

1. **覆盖**：需求基线全部 FR 有映射（P0 逐条可判定；P1 尽力；P2 显式列出标"二期"）；文末附 TC↔FR 覆盖矩阵 + 覆盖自检结论。
2. **断言方法学**（实战教训两条）：
   - 禁字面正则硬匹配易变文本（如 UI 标题）——改结构化解析（解析 JSON/清单字段断言语义）；
   - 扫描类断言必须排除定义源与工具缓存（哨兵值执行时随机生成、扫描面限被测产物/日志），杜绝自命中/恒假。
3. **实现无关**：契约表述不与实现命名耦合（逻辑场景名 SC-xxx 与套件输出的映射由核验剧本建立）。
4. **UI 项兜底**：无法自动化的视觉/手势项标"UI 手工 checklist + 证据类型"，且同 FR 必有自动兜底 TC。
5. **期望值可推导**：数值型期望附计算说明（实战例：消息数 4/10/18 = 每 prompt 1 user + 1 assistant × 发送数）。

## 6. 独立核验规范

1. 执行环境：干净检出标签、临时 HOME、随机哨兵凭证、离线 mock；证据头记录 `git describe --tags`、OS/Node/日期。
2. 判定四值：**PASS / FAIL / SKIP（P2 延后）/ MANUAL（UI 与环境受限：列遗留不计 FAIL，对应 FR 以自动兜底 TC 为门禁）**。
3. 压力抽查：对历史上 flaky 区域做并行负载连跑（≥5 次）；安全专项（脱敏/防 XSS）必须实测出证据。
4. 报告（`docs/verification/report-<hash>.md`）必含 7 件套：证据头、逐 TC 判定表、逐 FR 结论表、与上轮对比（缺陷逐项回归结论）、遗留清单、总结论、自检声明。
5. 证据归档 `docs/verification/evidence[-rN]/<TC-id>/`（cmd.txt + output.txt + 脚本原文；大输出截断注明）；一次性脚本在 /tmp。
6. **诚实条款**：FAIL 就报 FAIL；机械判据与语义不符处逐条披露，禁止修饰结论。

## 7. 协作、事件与故障处置

1. **失败回路**（核验 FAIL）：缺陷清单派回研发 → 修复 → 交付验收 → 重新打标签 → 新一轮核验；上限 N=2 轮，超限停止上报人类。基础设施故障（服务 503、工具面不可用）**不占**该额度，另账记录。
2. **瞬态故障处置**（实战 SOP）：
   - 中断后先查现场（`git status`/diff 与中断前对比），有半成品则保留并写明续做线索，无污染则声明；
   - 退避重试（≥270s 起步，指数拉长），禁止无脑连打；
   - 每次中断/重发在任务单留痕（含 invocation id）。
3. **工具面故障处置**：备用通道必须**明示后**启用，且隔离级别就高不就低（实战：pendant 不可用 → 原生 subagent；worktree 基目录 EACCES → 零写权暂存方案，产物落 /tmp 由总调度合入，保"一个工作区一个写者"）。
4. **交付验收**（总调度，收研发件时必做）：写权限核验 → FR 追溯表覆盖 → **亲自复跑自测**（不信自述）→ 稳定性抽查 → 提交打标签。缺项按"交付缺项"退回，不进核验。
5. 结论送达：PASS → 交付总结（结论/产物/证据索引/遗留/下一步）；FAIL → 缺陷清单+报告链接；blocked → 上报人类。

## 8. Git 与证据链规范

1. 提交信息标注产物作者（`git -c user.name="产品 Agent"` 等），正文注明性质（产出/修复/裁决/事件留痕）。
2. 标签即核验锚点：交付验收通过后打 `ready-for-verify[-rN]`（annotated，注明验收结论）。
3. 推送前检查：无真实密钥（`sk-…`/`ghp_…`/`AKIA…` 模式扫描）、无大文件、`.gitignore` 覆盖 node_modules/构建产物/vsix/harness 锁文件。
4. 事件留痕 commit 允许只有任务单变更（chore(tasks)），保证时间线完整可审计。

## 1. 目的与范围

本文档定义“多 Agent 研发流水线”的组织制度：一个总调度 Agent 统筹，产品 / 研发 / 测试三类专职 Agent 通过**仓库契约产物**协作，完成需求、开发与验证。目标是让功能验证全程无人介入，且结果可信、可追溯。

设计蓝本是人类研发组织（技术负责人 + PM + 开发 + QA），核心机制：

1. **角色专业化**：每个 Agent 只做一类事，提示词与权限按角色定制
2. **产物契约化**：Agent 之间不通过对话交接，只通过仓库内固定格式的文件交接
3. **验证独立化**：测试 Agent 全新上下文、只读源码、盲写用例，杜绝“自证”
4. **输入双通道**：需求输入可来自人类，也可来自 GitHub Issue（由总调度拉取分诊）

## 2. 角色定义与写权限矩阵

| 角色 | 职责 | 可写 | 禁写 |
|---|---|---|---|
| 总调度 Agent | 拉取输入、分诊派发、收产物、程序化检查、裁决失败回路、向人类/Issue 回写结论 | `docs/tasks/`（任务单与裁决记录） | 一切具体产物 |
| 产品 Agent | 把需求素材整理为需求文档（FR 编号、验收标准、边界） | `docs/requirements.md`、`docs/adr/` | `src/`、测试用例、验证报告 |
| 研发 Agent | 按需求文档与技术方案开发、自测、交付 | `src/`、`webview/`、`test/`（单测/集成）、`package.json` 等工程文件 | 需求文档、测试用例、验证报告 |
| 测试 Agent | 从需求文档盲写测试用例；产物交付后执行核验、出报告 | `docs/test-cases.md`、`docs/verification/` | `src/`、需求文档 |
| 评审 Agent（可选，二期） | 代码评审：架构符合性、安全、可测性 | `docs/reviews/` | `src/`、需求文档、测试用例 |

纪律三条：

1. 所有子 Agent 以**全新上下文**（fresh context）启动，互相不可见对方的推理过程
2. 权限由任务提示词声明 + 总调度在收产物时用 git 历史核验（越界写入 = 交付不合格）
3. 研发 Agent 不得写验证报告；测试 Agent 不得修代码（发现问题只出报告）

## 3. 输入通道（双通道）

### 3.1 通道 A：人类输入

人类直接向总调度提出需求（自然语言描述、参考链接、附件）。总调度整理为**需求素材**后派给产品 Agent。

### 3.2 通道 B：GitHub Issue 输入

总调度 Agent 从 GitHub 仓库拉取 Issue 作为任务来源：

- **触发**：定时巡检（cron）或人类指定 Issue 编号；目标为新建 Issue，或带 `agent:todo` 标签的既有 Issue
- **分诊**：总调度按标签/内容分类——`type:feature` / `type:bug` / `type:question`；question 类不进流水线，直接整理答案回写 Issue
- **素材标准化**：Issue 标题 + 正文 + 复现步骤 + 评论区讨论 一起构成需求素材；信息不足时总调度在 Issue 留言追问（@人类），该 Issue 挂起等待
- **去重与关联**：与已有需求/任务相似的 Issue 先做关联标注，避免重复派发
- **状态回写（闭环）**：
  - 开始处理 → Issue 加 `agent:in-progress`
  - 验证 PASS → 回写验证报告摘要 + PR/commit 链接，加 `agent:done`，feature 类在合并后关闭
  - 验证 FAIL 且重试超限 → 回写缺陷清单与报告链接，加 `agent:blocked`，留待人类裁决

### 3.3 输入模式与审批点的关系

| | 通道 A（人类） | 通道 B（Issue） |
|---|---|---|
| 审批点 1（需求基线） | 总调度裁决 | 总调度裁决 |
| 审批点 2（测试用例） | 总调度裁决 | 总调度裁决 |
| 结论送达 | 总调度向人类汇报 | 回写 Issue + 通知人类 |

> 2026-11-17 起（经人类批准的流程变更）：审批点统一由**总调度裁决**（按 §5 审查内容自行判定通过/退回），不再强制人类介入；`agent:auto` 豁免机制随之取消。人类仍可随时要求抽查、追加意见或恢复“人类必审”模式。结论送达义务不变；§8 的失败/冲突上报人类机制不在本变更范围。

## 4. 执行时序

```
人类(通道A) / GitHub Issue(通道B)
        │
        ▼
  ┌─ 总调度 Agent ─────────────────────────────┐
  │ ① 分诊 → 需求素材                            │
  │ ② 派产品Agent → 需求文档 ──【审批点1】──┐     │
  │ ③ 需求基线冻结                          │     │
  │    ├─ 派研发Agent：开发+自测（并行）      │     │
  │    └─ 派测试Agent：盲写用例 ─【审批点2】─┘     │
  │ ④ 研发交付(tag: ready-for-verify)            │
  │ ⑤ 派测试Agent(新上下文)：执行核验 → 验证报告  │
  │ ⑥ PASS → 交付总结/回写Issue                  │
  │    FAIL → 缺陷清单派回研发 → 回到④（有界重试）│
  └─────────────────────────────────────────────┘
```

关键时序约定：

- **②③ 并行**：研发与写用例同时进行，都只以需求基线为依据，互相不可见
- **④ 交付定义**：代码提交 + 自测全绿（`npm run verify:unit` / `verify:integration`）+ FR 追溯表 + 打标签 `ready-for-verify`
- **⑤ 核验定义**：在干净工作区检出标签，按 `docs/test-cases.md` 与验证剧本逐条执行，产出报告到 `docs/verification/`
- **完成定义**：验证报告逐 FR PASS 且证据齐全；总调度程序化检查报告格式完整后才算闭环

## 5. 审批点

> 2026-11-17 经人类批准：审批点由**总调度裁决**（按下列审查内容自行判定通过/退回），不再强制人类介入；人类可随时要求抽查或恢复“人类必审”模式。

| 审批点 | 时机 | 审查内容（总调度裁决） | 不通过的处理 |
|---|---|---|---|
| 1. 需求基线 | 需求文档产出后、任何开发前 | FR 范围/优先级/边界/验收标准 | 修订意见退回产品 Agent，重新提交 |
| 2. 测试用例 | 用例产出后、验证执行前 | 用例对需求的覆盖度、验收标准可判定性 | 退回测试 Agent 补充 |

审批点之后即为**基线冻结**：需求变更必须走“基线修订”（总调度评估影响面 → 总调度裁决，涉及范围/优先级变化时向人类通报 → 通知研发/测试双方），禁止静默修改。

## 6. 产物契约

```
docs/
├── requirements.md          # 产品Agent产出：需求基线（FR编号、验收标准、边界）
├── technical-design.md      # 研发Agent产出/维护：技术方案
├── test-cases.md            # 测试Agent产出：测试用例（TC编号 ↔ FR编号映射）
├── verification/
│   └── report-<git短哈希>.md  # 测试Agent产出：验证报告（逐FR结论+证据）
├── tasks/
│   └── <task-id>.md         # 总调度产出：任务单与裁决记录
└── agent-workflow.md        # 重定向存根（流程制度已收编至 DevelopmentGuidelines/development-guidelines.md 第二部分）
```

各产物的必填结构（总调度按此做完整性检查）：

- **requirements.md**：FR 编号表（含优先级、验收标准）、明确不做的范围、非功能需求
- **test-cases.md**：每条 TC 含 `TC-id ↔ FR-id`、前置条件、确定性操作步骤（Agent 可执行的命令/脚本，非人工点击）、期望结果、判定方式
- **交付物**：`ready-for-verify` 标签指向的提交 + FR 追溯表（FR → 实现文件位置）+ 自测输出
- **report-\<hash\>.md**：逐 TC 的 PASS/FAIL、证据引用（命令输出/报告文件/截图路径）、遗留问题、结论

## 7. 任务提示词模板（要点）

**产品 Agent**
> 你是产品 Agent。输入：<需求素材>。按本规范第二部分 §6 契约产出 docs/requirements.md。
> 只允许写该文件；不得涉及实现方案细节；每个 FR 必须有可判定的验收标准；明确列出不做范围。

**研发 Agent**
> 你是研发 Agent。依据 docs/requirements.md（基线）与 docs/technical-design.md 开发 <任务范围>。
> 允许写 src/、webview/、test/ 与工程文件；禁止修改需求文档、测试用例、验证报告。
> 完成定义：自测命令全绿 + FR 追溯表 + 提交并打标签 ready-for-verify。

**测试 Agent（写用例阶段）**
> 你是测试 Agent。仅依据 docs/requirements.md 编写 docs/test-cases.md。
> **禁止读取 src/ 与 webview/**（盲写）；每条 TC 必须是 Agent 可无人执行的确定性步骤；建立 TC↔FR 映射并自检覆盖所有 FR。

**测试 Agent（核验阶段，全新上下文）**
> 你是测试 Agent（核验）。在干净工作区检出 ready-for-verify 标签，按 docs/test-cases.md 逐条执行核验。
> 禁止修改任何源码与用例；逐条产出 PASS/FAIL 与证据引用；生成 docs/verification/report-<hash>.md。

**总调度 Agent**
> 你是总调度。负责分诊、派发、收产物、按契约做完整性检查、编排失败回路、维护 docs/tasks/。
> 不得替写任何角色的产物；失败回路最多 N 轮（默认 2），超限停止并上报人类/回写 Issue。

## 8. 失败回路与裁决

| 情形 | 处理 |
|---|---|
| 交付缺项（自测未过/追溯表缺） | 总调度退回研发 Agent，不进入核验 |
| 核验 FAIL（缺陷 ≤ 阈值） | 缺陷清单派回研发 Agent → 修复 → 重新打标签 → 重新核验 |
| 重试超过 N 轮（默认 2） | 停止流水线，标记 `agent:blocked`，上报人类裁决 |
| 需求发现歧义/缺漏 | 任意 Agent 报总调度 → 暂停 → 反馈产品 Agent 或人类（走基线修订） |
| 角色越界写文件 | 总调度以 git 历史认定交付不合格，退回重做 |
| Agent 之间结论冲突（如研发对缺陷有异议） | 总调度记录双方陈述到 tasks/，上报人类裁决，不得自行改判 |

## 9. 可信度保障（防作弊设计）

1. **自测 ≠ 核验**：研发自测只是准入门槛；测试 Agent 必须在干净工作区独立重跑
2. **盲写用例**：用例只从需求推导，防止迁就实现
3. **fresh context**：核验 Agent 不继承开发对话，只认仓库产物与可重复执行的命令
4. **证据留痕**：所有 PASS/FAIL 必须引用命令输出、报告文件或截图；总调度可抽查复跑
5. **确定性环境**：验证剧本依赖 mock provider 与固定脚本，任何人重跑结果一致
6. **git 即证据链**：写权限矩阵 + 提交历史，天然记录每个产物的作者与改动
