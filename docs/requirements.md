# Sdysyhj 需求文档

> Sdysyhj（山巅一石一壶酒）— Pi Agent for VS Code
>
> 状态：**待评审** ｜ 版本：v0.6 ｜ 更新日期：2026-11-21

---

## 1. 产品定位

Sdysyhj 是一个 VS Code 插件，将 Pi 编程智能体（coding agent）带入编辑器，提供对话式的代码阅读、编写、重构与命令执行能力。

**核心价值：**

- 在编辑器内以自然语言完成编程任务，无需切换到终端 TUI
- 与 pi 共享同一套会话、配置与凭证（`~/.pi/agent/`），终端与插件双端体验一致
- 开箱即用：不强制用户预先安装 pi CLI

**名称释义：** "山巅一石一壶酒"取首字谐音指代 Pi；仓库名 Sdysyhj 承载此意。

## 2. 目标用户与发布范围

| 项 | 决策 |
|---|---|
| 目标用户 | 先内部/个人使用，但按 VS Code Marketplace 可发布标准开发（打包、文档、兼容性测试齐备） |
| 运行时依赖 | 插件内置 `@earendil-works/pi-coding-agent`，免安装；同时优先使用 PATH 中已有的 pi CLI，失败时回退内置运行时 |
| 配置归属 | 完全复用 pi 自有配置（`~/.pi/agent/`：settings、auth、models）；插件 settings 仅存放 UI 相关项，避免两处配置打架 |

## 3. 术语表

| 术语 | 含义 |
|---|---|
| Pi / pi CLI | `@earendil-works/pi-coding-agent` 提供的编程智能体及其命令行程序 |
| RPC 模式 | Pi 的子进程集成模式（`pi --mode rpc`），JSONL 协议通信 |
| 会话（session） | Pi 的一次持续对话，含消息历史、分支、压缩状态，持久化为 JSONL |
| 工具调用（tool call） | Agent 执行 read/bash/edit/write 等工具的动作 |
| steer / follow-up | 运行中插话（steer）/ 排队等本轮结束再发送（follow-up） |
| 内置运行时 | 插件依赖中自带的 pi 运行时（`@earendil-works/pi-coding-agent` 包） |
| 实验面板 | TASK-009 阶段①新增的独立实验性 webview 面板（assistant-ui 迁移试点），非默认聊天面板，不影响既有面板行为 |
| 路线 A（fetch-bridge） | assistant-ui 官方 fetch 桥接路线：宿主侧 route handler 适配 PiBridge + webview 侧 useChatRuntime/vscodeFetch（`@assistant-ui/vscode`） |
| 路线 B（ExternalStoreRuntime） | 保留现有 postMessage 协议的路线：webview 侧 UiMessage→ThreadMessageLike 映射至 `@assistant-ui/react` ExternalStoreRuntime |
| golden fixture | 真实 pi 事件序列录制而成的静态回放文件（`test/fixtures/golden/`，TASK-008 落地），作离线验收数据源 |

## 4. 功能需求（MVP）

### 4.1 聊天（P0）

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-CHAT-01 | 流式对话 | P0 | 输入 prompt 后实时流式渲染回复（text delta 级别），不阻塞 UI（用户消息单次展示见 FR-CHAT-11） |
| FR-CHAT-02 | Markdown 渲染 | P0 | 回复支持标题、列表、表格、代码块（含语言高亮）、链接、行内代码 |
| FR-CHAT-03 | thinking 折叠 | P0 | 思考过程默认折叠为可展开块，展开后流式显示 |
| FR-CHAT-04 | 工具调用卡片 | P0 | 每个工具调用展示：工具名、关键参数摘要、执行状态（进行中/成功/失败）、可展开查看输入输出；bash 展示命令与输出摘要；大输出截断保留尾部并提供"复制全部" |
| FR-CHAT-05 | 中止运行 | P0 | 运行中可点击 Stop / 命令面板中止（对应 RPC `abort`），UI 恢复可输入态 |
| FR-CHAT-06 | steer 插话 | P1 | 运行中可继续输入，消息以 steer 方式排队注入；提供 steer/follow-up 模式切换 |
| FR-CHAT-07 | 错误展示 | P0 | provider 报错、子进程崩溃、未配置凭证等异常在聊天区展示可读信息与修复指引 |
| FR-CHAT-08 | 状态指示 | P0 | 顶部状态栏显示：当前模型、thinking 等级、运行状态（idle/streaming/aborted）、会话名 |
| FR-CHAT-09 | 流式输出自动跟随 | P1 | 运行状态为 streaming 时（自本轮流式输出开始计）：① 默认跟随——每轮流式开始即默认处于跟随态，跟随期间每次增量渲染后消息区视口保持"在底部"（"在底部"判定 = 视口底缘距滚动底端 ≤40px）；② 打断——用户向上滚动离开底部（距滚动底端 >40px）即停止自动跟随，后续流式增量不得为跟随而强制滚动（增量渲染不推动滚动位置，scrollTop 保持用户所选位置，尊重用户意图）；③ 恢复——用户滚回底部（距滚动底端 ≤40px）即恢复自动跟随，后续增量继续满足①的"在底部"跟随；④ 边界——跟随状态为会话内瞬时 UI 状态：不写入会话文件、不产生消息级标记、不跨插件重启持久化；运行状态为 idle 时不自动滚动（会话载入/切换的一次性初始定位不属本条"自动跟随"范畴） |
| FR-CHAT-10 | 聊天面板视觉规范 | P1 | ① 内容列居中：消息区与输入区（含底部模型选择器与上下文用量行）共享同一内容列，水平居中于面板，内容列最大宽度 = 960px（在 900–1100px 建议区间内定值；面板可用宽度超过上限时左右留白相等；CSS 口径：内容容器 `max-width: 960px` 且左右外边距 auto）；② 输入框圆角：输入框容器圆角半径 = 8px（CSS 口径：`border-radius: 8px`）；③ 发送图标化：发送动作为图标按钮（向上箭头/纸飞机样式图形），按钮内无文字标签，可访问性名称（aria-label 或 title）= "发送"；④ 消息布局：用户消息右对齐且由气泡容器包裹（带背景色与圆角的包裹元素）；助手消息左对齐且无气泡容器（不得有独立背景/边框的气泡包裹）；⑤ 时间替代角色标记：消息行不显示 User/Assistant 角色文字前缀，每条用户消息与助手消息展示时间戳，格式 HH:mm（24 小时制、本地时区；可断言正则 `^\d{2}:\d{2}$`）；thinking 折叠块与工具卡片自身的功能标签不属角色标记，不受本条约束 |
| FR-CHAT-11 | 用户消息单次展示 | P0 | 每条用户发送的消息（prompt，含运行中 steer / follow-up 插话）在聊天区恰好展示一条，计数单位 = 一次发送（同一文本多次独立发送仍逐条展示，不得因文本相同而跨发送合并）：① 单条恒成立——发送后即时（不等待 pi 确认回声）该消息即展示且可见条目数 = 1；在 pi 对该消息回发 user 确认（user 角色 `message_end`）后、本轮助手终稿渲染完成后两个判定时点，该条用户消息的可见条目数仍均为 1（不得出现第二条重复气泡）；② steer / follow-up 同口径——运行中以 steer 或 follow-up（FR-CHAT-06）方式发送的每条用户消息同样满足 ①；③ 历史重放不重复——面板关闭重开、或经 FR-SESS-03 切换会话后的历史重放中，每条用户消息可见条目数 = 1，重放内容与会话 JSONL 一致（澄清 #5 口径）；④ 文本保真——①–③ 任何判定时点，用户消息文本不得丢失、截断、拼接或错换为其他内容；pi 记录文本与发送原文不一致时，展示文本按澄清 #16 判定（以 pi 权威文本为准单条就地更新，更新前后均为一条）；⑤ 回归边界——助手消息（含 thinking 折叠、工具卡片，FR-CHAT-03/04）的条目数与内容展示不受本条影响 |

### 4.4 模型控制（P1）

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-MOD-01 | 切换模型 | P1 | 列出可用模型并切换（对应 `get_available_models` / `set_model`），三个等价入口：① 状态栏；② 命令面板；③ 底部内联选择器——输入区底部常显当前模型名，点击弹出可用模型列表，选中即切换并同步更新展示；任一入口切换后其余入口展示同步；切换持久化语义同 FR-MOD-03 |
| FR-MOD-02 | 切换 thinking 等级 | P1 | 同上（对应 `set_thinking_level` / `cycle_thinking_level`） |
| FR-MOD-03 | 会话内持久 | P1 | 切换结果随会话保留，重启插件后反映在状态栏与底部模型选择器（FR-MOD-01 入口③） |
| FR-MOD-04 | 上下文用量指示 | P1 | 输入区底部展示上下文用量：① token 权威取值 = 最近一条助手消息的 `usage.totalTokens`（`message_update` 携带的 Usage 对象）；② 上下文窗口 = `get_state` 返回的 `contextWindow`；③ 至少展示 token 数值（= ①）及其占上下文窗口的百分比（= ① ÷ ② × 100，四舍五入取整；数值允许千分位或 k 缩写格式）；④ 刷新时机：收到新的助手消息用量即刷新；切换会话后按新会话最近一条助手消息取值刷新；当前会话尚无助手消息时显示 "—" 占位；⑤ 既有 compaction 相关 toast 提示行为不变，不属本 FR 范围 |

### 4.5 命令与集成（P0/P1/P2）

| 编号 | 需求 | 优先级 | 验收标准 |

| FR-CMD-05 | pi 运行时来源 | P0 | 自动模式下：PATH 中存在可用 pi 时优先使用；PATH 无可用 pi 时使用插件内置运行时并能正常对话（开箱即用）；设置中可显式指定 pi 路径，指定后按该路径启动；显式路径无效或启动失败时展示含错误详情的可行动指引 |

## 5. 明确不做（MVP 边界外）

- **Diff & Apply**：Pi 的 edit/write 结果在 VS Code diff 视图确认后应用 —— **二期**（体验关键，但工作量大）
- **图片粘贴/拖拽**（`prompt` 的 images 参数）—— **二期**
- 多会话并行标签页 —— 二期
- 遥测/数据上报 —— 不做（如发布 Marketplace 再评估）
- 独立的凭证/模型配置界面 —— 不做，复用 pi 配置与 `pi auth`
- VS Code Chat API（Copilot 聊天面板）集成 —— 不做（已选自定义 Webview 路线）
- 流式跟随辅助 UI（"回到底部/跳到最新"悬浮按钮、跟随状态指示）与跟随行为设置项（开关/阈值配置）—— 不做（MVP 仅按滚动位置自动判定与恢复，见 FR-CHAT-09）
- 输入区独立"添加文件"按钮 —— 不做（v0.4 起 `@` 触发选择器为唯一文件引用入口，见 FR-FILE-02；资源管理器/编辑器右键发送 FR-FILE-03 保留）
- 用户消息「发送原文 / pi 权威文本」不一致时的对照展示、切换开关或原文查看入口 —— 不做（MVP 统一以 pi 权威文本单条就地更新，见澄清 #16）
- **TASK-009 阶段①不做项**（分期路线图：② 消息渲染 → ③ Composer 定制 → ④ 切默认面板删旧实现；各阶段范围届时另行基线修订，本期不立 FR）：不切换默认聊天面板（保持既有 vanilla 实现，阶段④才切换）、不删除/重写旧面板实现；实验面板不实现 @ 文件引用、`/` 命令菜单、模型选择器、上下文用量行、steer/followUp 队列 UI（阶段③ Composer 定制范围）；不做 Markdown 全量渲染对齐与 thinking/toolcall part 化工具卡（阶段②；本期最小渲染 = 纯文本级，见 FR-AUI-02③）；阶段①验收以 golden 回放为数据源，不要求接入真实 pi / 真实 provider（人工真机冒烟不禁止，但验收不依赖）

## 6. 非功能需求

| 编号 | 类别 | 要求 |
|---|---|---|
| NFR-01 | 性能 | 流式渲染不掉帧；面板切换/重开不丢当前运行状态；单次输出 10k+ tokens 时 UI 保持流畅 |
| NFR-02 | 稳定性 | Pi 子进程崩溃自动重启一次并提示；插件宿主异常不得导致 VS Code 不可用（进程隔离） |

## 7. 用户体验概要

**布局：** Activity Bar 新增 Sdysyhj 图标 → 侧边栏 Webview 聊天面板（自定义 UI，非 Chat API）。

```
┌──────────────────────────┐
│ Sdysyhj        [⚙][＋][🕘] │  ← 会话操作：设置/新会话/历史
│ ● claude-sonnet-4 · high  │  ← 模型/思维等级/状态，点击可切换
├──────────────────────────┤
│      帮我重构这个函数 14:02│  ← 用户消息：右侧气泡 + 时间（HH:mm）
│                          │
│ 好的，先看一下…      14:02 │  ← 助手消息：左侧、无气泡、Markdown 渲染
│   ▸ 💭 thinking…          │  ← 默认折叠
│   ▸ 🔧 read(src/a.ts) ✔   │  ← 工具卡片，可展开
│   （流式光标 ▍）            │
│ ⋯ 内容列水平居中 · 最大宽度 960px ⋯ │
├──────────────────────────┤
│ ╭──────────────────────╮ │  ← 圆角输入框（8px）
│ │ 输入消息…          [➤] │ │  ← 图标发送；@ 文件选择 / / 命令菜单
│ ╰──────────────────────╯ │
│ claude-sonnet-4 ▾  12.3k / 200k (6%) │  ← 底部：模型选择器 + 上下文用量
│ [■ Stop]  (运行中显示)     │
└──────────────────────────┘
```

**关键交互约定：**

- Enter 发送，Shift+Enter 换行；运行中发送框转为 steer 输入
- `@` 触发文件选择器（唯一文件引用入口，输入区无"添加文件"按钮）；`/` 开头文本触发命令补全菜单（↑/↓ 导航、Enter 选中插入、Esc 关闭，见 FR-CMD-03）
- 工具卡片默认单行摘要，点击展开输入/输出（输出截断 + "复制全部"）
- 中止后展示"已中止"标记，历史保留
- 无工作区打开时允许聊天，但提示文件工具受限（cwd = 用户主目录）

## 8. 验收标准汇总（MVP 发布门槛）

1. 从零安装插件（无需装 pi CLI）→ 打开面板 → 完成一次"读文件→修改→执行命令"的完整任务
2. 流式输出、工具卡片、thinking 折叠均符合第 7 节约定
3. 会话关闭 VS Code 重开后可从历史恢复，上下文完整
4. 三平台冒烟通过；`pi --mode rpc` 子进程崩溃可恢复并提示
5. 所有 P0 需求验收标准逐条勾选通过（口径 = §4.1–§4.5 MVP 功能需求的 P0 项；§4.6 FR-AUI 段为阶段①出口优先级，不入本条，见第 7 条与澄清 #18）
6. 发送 prompt（含运行中 steer / follow-up 插话）后，用户消息在聊天区各判定时点恰好一条；面板重开 / 会话切换的历史重放无重复用户气泡（FR-CHAT-11）
7. TASK-009 阶段①出口门禁（独立于第 1–6 条 MVP 门禁）：§4.6 全部「P0（阶段①）」项逐条通过；双切片对比报告（FR-AUI-06）交付；默认面板既有行为零变更（第 1–6 条 MVP 门禁与既有 verify 套件回归全绿）

## 12. 验收标准澄清（历次裁决）

> 历次验收口径澄清（逐项裁决）：除注明外仅澄清验收口径，不变更 FR 范围/优先级，FR 表格本体维持原状。#1–#10 为测试 Agent 上报歧义（v0.2.1）；#11–#13 为核验阶段歧义（v0.2.2）；#14 为 GitHub Issue #2 / 缺陷 #D-03（v0.2.3）；#15 为通道 A 素材口径澄清（v0.4）；#16 为 TASK-008 缺陷修复口径澄清（v0.5，随 FR-CHAT-11 新增）；#17 为 TASK-008 审批点 2 口径澄清（v0.5.1）；#18 为 TASK-009 阶段①优先级与门禁归属口径（v0.6）。

1. **#1 FR-CMD-03 门禁边界**：MVP 门禁仅含 P0（依 §8-5）；FR-CMD-03 整条为 P2，不计入 MVP 门禁；"命令文本直接发送即可生效"作为 prompt 透传可用性的辅助判定（不阻塞门禁）。（v0.4 注：FR-CMD-03 优先级已调整为 P1、进入本期范围（见 §11），"不计入 MVP 门禁"结论不变。）
2. **#2 FR-CHAT-04 截断阈值**：默认保留尾部 200 行（对应配置 `sdysyhj.outputTailLines` 默认 200）；超过阈值即截断展示且保留尾部；"复制全部"取完整输出。
3. **#3 NFR-01 量化判据**：采用可判定代理指标——≥10k tokens（≥600 delta）零丢失 + 全量渲染完成 ≤30s + 渲染批处理（增量合并）迹象；FPS/主观流畅不作硬性判定，录屏仅作辅助证据。
4. **#4 FR-CMD-05 "可用 pi"判据**：`pi --version` 退出码 0 且输出含版本号，且版本不低于插件声明的最低支持版本；否则回退内置运行时。
5. **#5 FR-SESS-03 "与 pi 端行为一致"等价判据**：切换会话后重放的历史消息与会话 JSONL 一致（含压缩状态），UI 重建历史完整；除此之外不作独立判定。
6. **#6 FR-CHAT-08 交互归属**：状态栏"点击可切换"的行为归 FR-MOD-01/02 判定；FR-CHAT-08 仅判定四字段展示与状态流转。
7. **#7 FR-SESS-07 检测边界**：会话文件路径/格式属实现细节（由技术基线/核验剧本定义），需求层判定边界 = 外部修改后 ≤5s 内提示刷新且不静默继续使用陈旧状态。
8. **#8 NFR-03 位置边界**："pi 原有位置" = `$HOME/.pi/agent/`（settings/auth/models/会话存储）；插件不得在其他位置落盘会话/状态副本。
9. **#9 §8-1 "从零安装"离线等价口径**：`vsce package` 产出 vsix 本地安装 + PATH 无 pi + 无预置凭证 + mock provider；离线/CI 环境以此为准。
10. **#10 FR-MOD-02 枚举取值**：thinking 等级取值以 pi 侧权威返回为准（需求不固化枚举）；UI 透传展示。
11. **#11 运行状态口径**：运行状态取值为 idle/streaming（error/restarting 为瞬态）；"已中止"是运行结果标记（消息级），不是运行状态；中止（abort）后运行状态必须回到 idle、UI 恢复可输入（与 FR-CHAT-05 及技术设计 §3.2 状态图一致）。
12. **#12 FR-SESS-02"消息数"口径**：= 会话内消息总数（user 消息 + assistant 消息合计）。
13. **#13 FR-SESS-07"不静默继续使用陈旧状态"释义**：检测到外部修改后必须阻止陈旧状态继续被使用——拦截后续交互直至刷新完成，或自动刷新；仅展示提示但继续受理交互 = 不满足验收标准。
14. **#14 `extension_error` 展示通道（FR-CHAT-07 边界）**：pi 运行时扩展系统的 `extension_error` 事件属上游扩展通知——展示通道 = 非阻断通知（toast，一次性），不得进入 FR-CHAT-07 的聊天区错误卡片；完整字段（extensionPath/event/error）必须写入 Output 日志（Sdysyhj 频道，对应 FR-CMD-02 / NFR-05），不得丢弃；同一错误（相同 extensionPath + error）窗口期内去重展示，日志仍全量记录。FR-CHAT-07 本身不变：错误卡片范围 = 需用户行动的错误（provider 报错、子进程崩溃、凭证缺失等）。
15. **#15 素材口径"触发旋转"（v0.4，TASK-006 素材②）**：通道 A 素材原文"输入 @ 触发旋转"中的"触发旋转"，统一按"触发选择"理解——即键入 `@` 弹出文件选择器（FR-FILE-02）；"旋转"判定为"选择"之笔误，不产生任何旋转类视觉/动画需求。
16. **#16 用户消息展示文本以 pi 权威文本为准（v0.5，TASK-008 / FR-CHAT-11）**：当 pi 侧记录的用户消息文本与用户发送原文不一致时（如 pi 对 slash 命令、`@file` 引用作展开改写，或 steer 排队后文本被改写），唯一口径 = **以 pi 权威文本为准、单条就地更新**——pi 确认回声到达前展示发送原文，到达后该条目文本更新为 pi 权威文本，更新前后条目数均为 1（不得新增条目，不得同时展示两版文本）；历史重放（FR-SESS-03 / 澄清 #5）中的用户消息文本同以会话 JSONL 为准。理由：#5 已钉死「历史重放与会话 JSONL 一致」，若保留发送原文，同一条消息将在面板重开 / 会话切换后变为另一文本，实时展示与历史重放互相矛盾；就地更新使两处始终同源，且用户所见即 pi 实际处理的文本。
17. **#17 不可关联回声的保守展示（v0.5.1，TASK-008 / FR-CHAT-11，总调度审批点 2 裁决）**：澄清 #16 覆盖「回声可关联」路径；当 pi 回声文本与全部待确认用户消息条目均无法唯一关联（多通道不可判定）时，「到达后更新为权威文本」无确定目标条目。唯一口径 = 该场景为 #16 的**受控例外**：各用户消息条目恒 1 条、文本不错换、不因该回声新增条目，实时窗口保留发送原文；经会话切换/刷新/面板重开的权威重建后，文本收敛为会话 JSONL 权威文本（澄清 #5、#16 末句）。产品语义不变：单条与不错换优先于即时权威化。
18. **#18 阶段① FR 优先级与门禁归属（v0.6，TASK-009 / §4.6）**：§4.6 FR-AUI 段的「P0（阶段①）/P1（阶段①）」为**阶段①出口门禁口径**（P0 = 阶段①发版阻塞项、逐条可判定；P1 = 尽力），不进入 §8-5「所有 P0 需求逐条通过」的 MVP 发布门禁。理由：阶段①为实验性质，不改变默认面板任何用户可见行为（FR-AUI-01 零变更约束），MVP 已发版（v0.1.6），以可行性探针阻塞常规发版倒置风险优先级；阶段①交付以 §8 第 7 条出口门禁判定（FR-AUI P0 项全过 + 对比报告交付 + 既有 MVP 门禁回归全绿）。阶段②③④ FR 本期不立（路线图见 §5 注记），届时另行基线修订。
