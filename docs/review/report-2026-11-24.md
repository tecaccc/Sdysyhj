### R-05 ｜ P1 ｜ §4.1 ｜ v0.1.8 流式渲染性能回退：五道门禁全绿仍放行的结构性剖析（触发事件，缺陷编号待登记）

- **现象**：TASK-009 切换批次（19588eb → v0.1.8）发版后，真实使用暴露流式渲染性能回退；核验 report-19588eb 总结论"32 项自动化 PASS + 4 项 MANUAL（非门禁）+ 产品缺陷 0"。
- **证据（为什么没拦住，逐道门禁）**：
  1. **NFR-01 验收判据不度量流畅度**：需求基线澄清 #3 将"流式渲染不掉帧"代理化为"≥600 delta 零丢失 + 全量渲染 ≤30s + 批处理迹象"（docs/requirements.md:225）——三条均为正确性/完成性判据；且核验环境为 jsdom（无布局无渲染成本），"≤30s"在该环境近乎恒真。
  2. **FR-AUI-08「功能等价」只定义功能语义等价，不含质量属性等价**：等价域 TC-115~136 全部为语义/结构断言，无一条同负载性能对比。旧实现的 300ms 节流 Markdown 重排（webview/render/messages.ts:2、:69）只存在于技术设计描述（technical-design.md:288），**从未进入任何验收条款**——迁移时无义务保留，等价判定也无从发现丢失。
  3. **自动化面无任何性能计时断言**：核验 TC-105~108 度量的是 bundle 字节（预算 4MiB 用 23.8%）与 CSP 指令面——体积绿 ≠ 渲染快。
  4. **唯一能感知性能的通道（真机 MANUAL）标记为非门禁**：TC-125（观感/IME/焦点）、TC-114 等四值 MANUAL"遗留不计 FAIL"——制度上把人类感知通道排除在门禁外。
- **证据（机制级根因，代码锚点 + 频率算术）**：
  - 旧经典面板：delta → rAF 合批的 `textContent` 追加（O(delta) 廉价 DOM 写）+ **Markdown 重排按 300ms 节流**（webview/render/messages.ts:69）；
  - 新 UI：`EventBuffer` 每 **rAF**（≤60Hz）一次 store 演进 + 单次通知（webview/ui/store.ts:338-345）→ React 全量 reconciliation → `MarkdownTextPrimitive`（webview/ui/markdown.tsx:46，`defer` 为官方懒挂载渐进，非增量解析）对**全文**重新走 remark 链——react-markdown 无增量解析；
  - 算术：流式中 Markdown 全文重析频率由 ≈3.3Hz（300ms）升至 ≤60Hz（rAF）≈ **18×**，每次解析 O(消息全文)；10k+ token 单消息流式尾段 = 每帧全量重析饱和主线程；
  - 附加放大项（同文件）：`uiReducer` 每个 delta 事件执行 `[...state.messages]` 数组拷贝 + `copyBlocks`（store.ts `applyMessageEvent`/`appendDelta`）——每帧成本 O(该帧 delta 数 × 全会话消息数)，长会话下二次放大。旧实现为尾部 DOM 追加，无全会话重算。
  - 真机 CPU/帧率/内存实测：**待定性**（超本轮 headless 只读能力；机制与频率算术可复现，建议缺陷单登记后随修复批次真机剖析补数）。
- **影响面**：v0.1.8 全部用户的长回答流式体验（严重度 P1，与规范 §7 判例一致）；长会话二次劣化。
- **b) 同类盲区（修类，jsdom + 小载荷 fixture + 终态断言这一验证栈结构性看不见的清单）**：① 交互帧率/主线程占用（本案例）；② 长会话内存增长（reducer 全量拷贝模式）；③ 单条大 Markdown 消息的重析成本；④ 真实 CSP 执行（jsdom 不执行 CSP，R9 报告自认，TC-108 MANUAL）；⑤ 滚动几何（jsdom scrollHeight=0，R9 报告 TC-123 载体注记自认）；⑥ 首字延迟等感知类时延。→ 全部落入 P-01/P-02 提案。
- **提案**：缺陷单正式登记（编号待定，去向见 ledger R-05）；修复方向 = EventBuffer 对 text/thinking 增设 ≥300ms 量级的重排节流（或等价的增量渲染），并按 P-01 建立新旧同负载对比基线。
